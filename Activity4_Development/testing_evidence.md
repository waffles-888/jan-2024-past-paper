# Activity 4 – Testing Evidence

## Instructions

The purpose of this activity is to demonstrate that your software solution has been thoroughly tested and functions as intended.

Testing is an important part of software development as it helps identify errors, validate requirements, and improve the reliability of the final product.

You should complete all sections of this document and provide evidence to support your testing process.

---

## Before You Begin

Before carrying out testing, ensure that you have:

- Completed your program development.
- Reviewed the original project requirements.
- Identified the features and functions that need testing.
- Prepared suitable test data.

Remember that good testing should include:

- Normal data
- Boundary data
- Extreme data
- Invalid data

---

## Task 1: Record Your Test Results

For each test:

1. State the purpose of the test.
2. Enter the test data used.
3. Record the expected result.
4. Run the program.
5. Record the actual result.
6. Identify whether the test passed or failed.

You should test every major feature of your software solution.

---

## Task 2: Provide Evidence

For each test, include evidence where appropriate.

Evidence may include:

- Screenshots
- Output from the program
- Error messages
- Code snippets
- Demonstrations of successful functionality

Evidence should clearly show the outcome of the test.

---

## Task 3: Record Problems and Fixes

If a test fails:

1. Describe the problem identified.
2. Explain what caused the issue.
3. Describe the changes made to fix it.
4. Retest the solution.
5. Record the new result.

This demonstrates your debugging process and shows how the software was improved during development.

---

## Task 4: Test Using Different Types of Test Data

Your testing should include a range of test data types.

### Normal Data

Typical inputs that a user would be expected to enter.

**Example:**

```text
Password: Abc123!@
```

Expected outcome:

```text
Program accepts input and processes correctly.
```

---

### Boundary Data

Inputs at the minimum or maximum acceptable limits.

**Examples:**

```text
Minimum password length
Maximum password length
```

Expected outcome:

```text
Program handles limits correctly.
```

---

### Extreme Data

Inputs at the very edge of the accepted range.

**Examples:**

```text
Smallest valid value
Largest valid value
```

Expected outcome:

```text
Program processes the values without errors.
```

---

### Invalid Data

Inputs that do not meet the validation rules.

**Examples:**

```text
Blank input
Special characters
Text entered instead of a number
```

Expected outcome:

```text
Appropriate error message displayed.
```

---

## Task 5: Review the Results

After completing all tests:

- Review your results.
- Identify any common issues.
- Confirm that all major requirements have been tested.
- Ensure that all critical bugs have been resolved.

---

## Task 6: Complete the Testing Summary

At the end of the document:

### Bugs Identified

List any bugs discovered during development.

For each bug describe:

- The issue.
- How it affected the program.
- How it was resolved.

---

### Changes Made

Summarise the improvements made as a result of testing.

Examples may include:

- Improved validation.
- Fixed calculation errors.
- Improved user feedback.
- Corrected logical errors.

---

### Overall Outcome

Write a short summary explaining:

- Whether the solution met the testing requirements.
- Whether any bugs remain.
- How confident you are that the software works as intended.
- How testing improved the quality of the final solution.

---

## Submission Checklist

Before submitting, ensure you have included:

- [ ] Purpose of each test
- [ ] Test data
- [ ] Expected results
- [ ] Actual results
- [ ] Pass/fail decisions
- [ ] Testing evidence
- [ ] Bugs identified
- [ ] Fixes implemented
- [ ] Testing summary
- [ ] Evidence of retesting where required

---

## Assessment Tip

Higher-quality testing evidence demonstrates a systematic approach to testing. You should test all major features, use a range of test data types, record evidence clearly, and explain how testing led to improvements in the final solution. Simply recording that a test passed is not enough; you should show what was tested, what happened, and what actions were taken as a result.
